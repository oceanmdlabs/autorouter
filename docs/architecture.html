Event Streams
Three ways events enter the system
FHIR Messages eReferral
server/api/fhir/[...fhirPath].ts
→ process-message.controller.ts
Ocean pushes FHIR R4 Bundles when a referral is created, accepted, declined, cancelled, or messaged. The controller extracts event context and passes it to the service request use case.
Patient Engagement Webhooks Open API
server/api/openapi/webhook/[clientId].ts
→ process-patient-engagement-event.use-case
Ocean's patient portal sends webhooks when patients complete forms or add notes. The handler fetches patient and note via Open API, then runs PE event rules. Rate-limited + replay-protected in memory.
CDS Hooks Pre-submission
server/api/cds/cds-services/order-sign-cds.ts
CDS hooks fire before a referral is submitted. Only showCdsCard is available here. Rules using request_pre_submission return advisory cards back to the clinician's EHR.

Routing Rule
The core domain object
Defined in src/entities/models/routing-rule.ts · persisted in the routing_rules table
triggeringEvent
RoutingEventType
Which of the 10 event types activates this rule. A rule only runs when its event fires.
prompt
string
Natural language instructions for the LLM — what to check, when to act, what not to do.
enabledTools
RoutingToolName[]
Which of the 13 tools the AI is allowed to call. Tools not in this list are hidden from the model for this rule.
allowedContextFields
"age" | "gender" | "postalCode" | "attachments"
Patient data the AI can see. Attachments require a separate privacy acknowledgement to enable.
priority
number (int, positive)
Higher value runs first. Ties resolved by createdAt asc, then id asc. Drag-to-reorder in the UI.
stopProcessingOnMatch
boolean
When true and the rule fires with valid actions, all lower-priority rules are skipped and marked stopped.
active
boolean
Inactive rules are skipped during evaluation and logged as "rule is inactive."
summarizeAttachmentsAcknowledged
boolean
Privacy gate — must be true before the attachments context field can be enabled.
Rule Evaluation Engine
How rules are processed per event
01
Load all rules in priority order
Repository returns rules sorted by priority desc, then createdAt asc. All rules for the tenant are fetched once.
src/infrastructure/repositories/routing-rules.repository.ts
02
Check AI opt-out
If the FHIR QuestionnaireResponse has ai_opt_out=true, skip all evaluation. Logged as "Patient has opted out."
evaluate-rule.service.ts → avoidProcessingDueToPatientOptOut()
03
Pre-summarize attachments once
If any rule has attachments in allowedContextFields and the event has attachments, summarize them once before the rule loop. The summary string is reused by all rules — never re-generated per rule.
process-service-request-event.use-case.ts → ai.service.summarizeAttachments()
04
Iterate rules sequentially
For each rule: skip if inactive or wrong event type. Build evaluation prompt + filter tool set to rule's enabledTools. Call AI. Return tool calls as planned actions.
src/application/use-cases/evaluate-rules-in-order.ts · evaluate-rule.service.ts
05
Apply stop-processing
If a triggered rule has stopProcessingOnMatch=true and returned valid actions without error, all subsequent rules receive stoppedByRuleId and are skipped without an AI call.
src/application/use-cases/evaluate-rules-in-order.ts
06
Filter blocked email actions
If an email allowlist is configured in SiteConfiguration, sendEmail actions targeting unlisted addresses are removed before execution.
src/application/use-cases/filter-blocked-email-actions.ts
07
Execute actions for triggered, non-skipped rules
Rules with stoppedByRuleId are skipped entirely. For triggered rules, each planned tool action is executed sequentially. Errors are caught and logged but don't halt other rules.
src/infrastructure/services/routing-tool-action.service.ts
08
Write LLM decision audits
Each rule evaluation → one llm_rule_decision_audit row (EXECUTE/SKIP/ERROR, reasoning). Each tool execution → one llm_rule_tool_execution_audit row (status, timing, input hash, result).
src/application/use-cases/write-decision-audits.ts
09
Write activity log entry
One activity_log_entry per event containing a JSON summary of all rule decisions and tool results, with full-text search indexing.
process-service-request-event.use-case.ts (final step)

AI Integration
LLM providers & tool calling
OpenAI
Default: gpt-4.1-mini
Default when not configured. Structured tool calls via Vercel AI SDK.
Google
Default: gemini-2.5-flash
Multimodal — supports images and PDFs for attachment summarization.
Cohere
Default: command-a
command-a-03-2025 in code.
AWS Bedrock
Default: claude-3-sonnet
IAM credential chain. Mistral on Bedrock falls back to text-parsed tool calls.
Per-rule evaluation: Build prompt → filter registry to rule's enabledTools → ai.service.getToolCalls(prompt, toolSet) → structured tool calls → map to RoutingToolAction[].

Attachment summarization: Called once before the rule loop via ai.service.summarizeAttachments(). Multimodal generateText for PDFs and images. Image errors fall back gracefully to non-image content only, with a note appended.

Provider per tenant: Configured in site_config.aiProvider + aiApiKeyEncrypted + aiModel. Resolved at evaluation time from SiteConfiguration.
Multi-Tenancy
Tenant isolation model
Every table has a tenant_id column. All repository queries are automatically scoped — rules, logs, erequests, site config, healthcare services, audit records.

ApplicationContext.getTenantId() returns the current tenant from the session (user.activeTenantId ?? user.tenantId). Users can belong to multiple tenants via tenant_memberships and switch between them. The activeTenantId on the session controls which tenant is active.

The clientId in site_config routes patient engagement webhooks to the correct tenant without a user session. The OAuth2 clientId/clientSecret pair authenticates inbound FHIR messages. Each tenant has exactly one SiteConfiguration holding all credentials.
