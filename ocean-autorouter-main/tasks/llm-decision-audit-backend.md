Goal
Add decision auditability for LLM-driven rule evaluations, with no PHI, and with a feature-flagged rollout. We want to
be able to take a (referralId, ruleId /rule name) and answer:

- What was the decision (EXECUTE or SKIP)?
- What was the confidence?
- What was the reason (concise, non-PHI)?
- If EXECUTE, what tools were planned and what happened when they executed (per tool outcome)?

Scope for this iteration (keep it simple)

- Decision, reasonSummary, confidence, and minimal model metadata.
- No promptInfo.
- No guardrails object.
- matchedSignals is optional: include ONLY if it provides value without PHI. If hard, omit for now.
- Absolutely no PHI stored in audit tables or in model outputs.
- Implement behind a feature flag so we can disable quickly if needed.

Current behavior

- event comes into the system via webhook
- system determines candidate rules if any
- Builds a prompt and calls the LLM,
- LLM currently returns tool calls directly; system executes them.
- We want to move toward JSON output that describes the decision and tool plan.

Key invariant

- Each rule evaluation results in exactly one of:
    - EXECUTE: run the tool plan returned by the LLM (one or more tools)
    - SKIP: run no tools
- Tools and args must be explicit when decision is EXECUTE, because arguments may be generated by the LLM.
- If required args are missing or invalid, default to SKIP and audit why.

Safety constraints

- Do not send patient email addresses to the LLM. - is already the case we only pass emailConsent = true or false.
- Do not allow PHI in:
    - decision reason
    - tool rationales
    - audit tables
    - tool args (unless the arg is explicitly allowed and is already a non-PHI identifier such as referralId)
- If the model attempts to include PHI, treat output as invalid and default to SKIP.

Feature flags

- Add a feature flag (example: LLM_RULE_JSON_DECISION_AUDIT) with modes:
    - OFF: existing behavior only
    - SHADOW: run existing behavior, and also run JSON-decision evaluation and store audit rows, but do not change
      execution path
    - ON: use JSON-decision evaluation for execution and auditing
- Start with SHADOW, then ON after validation.

Deliverable 1: Update LLM output format to JSON (minimal envelope)
The LLM must output ONLY valid JSON. No prose. No markdown. No tool-call format.

JSON shape (minimal)
{
"referralId": "string",
"rule": {
"ruleId": "string",
"ruleName": "string",
"ruleVersion": "string"
},
"decision": "EXECUTE" | "SKIP",
"reasonSummary": "string (concise, non-PHI)",
"confidence": number (0.0 to 1.0),
"tools": [
{
"toolName": "string",
"args": { },
"rationale": "string (non-PHI)"
}
],
"model": {
"name": "string",
"requestId": "string"
}
}

Rules for tools field

- If decision == "SKIP": tools MUST be [].
- If decision == "EXECUTE": tools MUST be non-empty.
- toolName must be from the rule's allowed tool list.
- args must validate against a per-tool args schema (defined in code, not by the model).
- If any toolName or args are invalid, treat output as invalid and default SKIP, and record audit.

Example EXECUTE
{

"rule": { "ruleId": "cardiac-risk-assessment", "ruleName": "Cardiac Risk Assessment Auto Accept", "ruleVersion": "
1.3" },
"decision": "EXECUTE",
"reasonSummary": "Reason for referral matches cardiac risk assessment. Rule configured to auto accept and post booking
instructions.",
"confidence": 0.92,
"tools": [
{
"toolName": "ocean.autoAcceptReferral",
"args": { "referralId": "R-12345" },

},
{
"toolName": "ocean.addReferralMessage",
"args": { "referralId": "R-12345", "messageType": "BOOKING_INSTRUCTIONS", "messageText": "Static booking instructions from rule config." },
"rationale": "Add booking instructions after acceptance."
},
{

"rationale": "Notify staff about the automated action."
}
],
"model": { "name": "YOUR_MODEL_NAME", "requestId": "req-abc" }
}

Example SKIP
{
"referralId": "R-67890",
"rule": { "ruleId": "cardiac-risk-assessment", "ruleName": "Cardiac Risk Assessment Auto Accept", "ruleVersion": "
1.3" },
"decision": "SKIP",
"reasonSummary": "Reason for referral does not match cardiac risk assessment or synonyms.",
"confidence": 0.88,

Prompt template requirements

- Include the allowed tools list and per-tool args schema for THIS rule.
- Instruct the model to:
    - output only JSON matching the schema above
    - always include decision, reason, confidence
    - if EXECUTE, include tools with exact args that match the provided schemas
    - if any required arg is unknown or cannot be derived safely, output SKIP with a reason like "Missing required tool
      argument"
    - never include PHI, never include patient email
    - never invent config values: use placeholders like CLINIC_ADMIN_EMAIL_FROM_CONFIG when appropriate

Deliverable 2: Audit persistence (new DB tables)
Add two new tables: one for decisions, one for tool executions. No PHI in any column.

Table A: llm_rule_decision_audit
One row per (site_id, referral_id, rule_id, evaluation_run_id). Keep it easy to query by referral_id and rule_id.

Required fields:

- id (pk)
- site_id (if applicable)
- referral_id
- rule_id, rule_name, rule_version
- decision (EXECUTE|SKIP|ERROR)
- confidence (0.0-1.0)
- reason (short, non-PHI)
- model_name
- model_request_id
- validation_status (VALID|INVALID_JSON|INVALID_SCHEMA|DISALLOWED_CONTENT|OTHER)
- validation_error (short string)
- created_at

Indexes:

- (site_id, referral_id, rule_id, created_at)

Table B: llm_rule_tool_execution_audit
One row per tool execution attempt, linked back to decision_audit.id.

Required fields:

- id (pk)
- decision_audit_id (fk -> llm_rule_decision_audit.id)
- site_id, referral_id, rule_id (duplicated for fast filters)
- tool_index (int) to preserve order
- tool_name
- args_hash (sha256 of canonicalized args JSON)
- status (PLANNED|SUCCESS|FAILED|SKIPPED)
- error_code (string)
- error_summary (short, non-PHI)
- started_at, finished_at
- created_at

Indexes:

- (site_id, referral_id, rule_id)
- (decision_audit_id, tool_index)

Execution rules

- When decision is VALID and EXECUTE:
    - insert decision row
    - insert tool rows with status PLANNED (one per tool)
    - execute tools in order
    - update each tool row to SUCCESS or FAILED with timestamps and error summary
- When decision is SKIP:
    - insert decision row
    - no tool rows (or optionally insert zero rows)
- When output invalid:
    - insert decision row with decision ERROR or SKIP (pick one standard)
    - validation_status and validation_error filled
    - no tool rows
